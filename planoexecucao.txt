LEMBRETE - COMO ABRIR O PROJETO LOCAL NO DIA A DIA
Este lembrete vale para um computador JÁ CONFIGURADO, com .env, volume e tabelas.
Em outro computador, fazer primeiro a instalação descrita logo abaixo.
Depois de reiniciar o computador ou encerrar os serviços:
1. Abrir o Docker Desktop e aguardar a inicialização.
2. Abrir um terminal PowerShell na raiz do projeto e executar:
   docker compose up -d --wait
   docker compose ps
   O primeiro comando inicia/confere o banco; pode ser repetido sem recriar dados.
   O segundo apenas mostra a situação e é opcional para conferência.
   Não iniciar o container manual antigo findy-postgres junto com o Compose.
3. Iniciar o backend, se não estiver rodando:
   .\backend\plataformaservicos\start-local.ps1
   Deixar o terminal aberto e aguardar Started PlataformaservicosApplication.
4. Abrir http://localhost:8080/index.html.
   Não precisa de Live Server nem repetir os testes a cada início.
5. Ao terminar: Ctrl+C no backend e docker compose stop para parar o banco.
Não reinstalar ferramentas, recriar volume, substituir .env ou repetir SQL
para o uso diário. Os dados permanecem no volume existente.
Para acessar apenas o site publicado, não é necessário iniciar o Docker local.

2. RODAR O PROJETO NO COMPUTADOR DO COLEGA (WINDOWS / POWERSHELL)
Este caminho cria um banco LOCAL PRÓPRIO, separado do seu banco e do Neon.
Pré-requisitos: Git, Java/JDK 21 e Docker Desktop instalados e funcionando.
Maven Wrapper já está no projeto; o primeiro início precisa de internet para
baixar o Maven/dependências, caso ainda não estejam no computador.

2.1 - Obter a versão correta do código
Na pasta em que deseja guardar o projeto:
  git clone --branch bancofuncional https://github.com/otaviograu1654/SITE-FINDY.git
  cd SITE-FINDY
O nome da pasta criada pelo clone é SITE-FINDY (com hífen).
Se o repositório exigir autenticação, o colega precisa de acesso próprio.
Mudanças que só existem no seu computador, sem commit/push, NÃO chegam no clone.
Antes de testar a versão nova juntos, disponibilizar os arquivos atuais por Git
ou por uma cópia do projeto sem .env/credenciais. Não foi feito commit/push nesta
atualização. Se a branch mudar no futuro, usar a branch combinada pela equipe.

2.2 - Preparar o banco novo (somente na primeira instalação)
Na raiz do projeto, com Docker Desktop aberto:
  Copy-Item .env.example .env
Editar o NOVO .env e escolher sua própria POSTGRES_PASSWORD. Não copiar a senha
do banco de outra pessoa. O exemplo usa banco findy, usuário postgres, porta
5433 e volume findy_postgres_data. Manter esses nomes nos comandos abaixo ou
ajustá-los de acordo com a configuração escolhida. Não substituir um .env já
configurado nem reaproveitar um banco com dados sem revisar antes.
  docker volume create findy_postgres_data
  docker compose up -d --wait
  docker compose ps
O Compose usa volume externo e NÃO cria as tabelas do Findy automaticamente.
O volume precisa existir; criar o volume não importa registros de outro PC.

2.3 - Criar as tabelas e categorias (SOMENTE BANCO NOVO E VAZIO)
Executar uma vez na raiz, na ordem abaixo. O Hibernate apenas valida o esquema.
Não usar este bloco no banco local já pronto, no Neon ou para atualizar dados.
Os scripts antigos de criação não são incrementais e não devem ser repetidos.

  $OutputEncoding = [System.Text.UTF8Encoding]::new($false)
  $findyScripts = @(
    'usuario_e_prestadores.sql',
    'categorias.sql',
    'servicos.sql',
    'solicitacoes.sql',
    'avaliacoes.sql',
    'recuperacao_senha.sql',
    'fotos_usuarios.sql',
    'cadastro_profissional.sql',
    'contratacao_real.sql'
  )
  foreach ($findyScript in $findyScripts) {
    Get-Content -Raw -Encoding UTF8 (Join-Path database $findyScript) | docker compose exec -T postgres psql -U postgres -d findy --set=ON_ERROR_STOP=1
    if ($LASTEXITCODE -ne 0) { throw "Falha em $findyScript. Pare e confira o erro antes de continuar." }
  }

Esse bloco cria a estrutura e as sete categorias, sem importar profissionais
fictícios ou contas reais. dados_demonstracao.sql é opcional e está documentado
em database/README.md; não é necessário para a aplicação funcionar.
Em uma instalação existente, aplicar apenas os incrementos ainda necessários,
conforme CADASTRO_PROFISSIONAL.md e CONTRATACAO_REAL.md, sem recriar tabelas.

2.4 - Iniciar a aplicação completa
Na raiz, depois do banco estar saudável e das tabelas existirem:
  .\backend\plataformaservicos\start-local.ps1
Aguardar Started PlataformaservicosApplication e abrir:
  http://localhost:8080/index.html
O backend serve HTML/CSS/JavaScript e a API no mesmo endereço. Não é preciso
Live Server. O terminal do backend e o Docker precisam continuar funcionando.
Depois da primeira instalação, usar somente o lembrete do início deste arquivo.
As funções de e-mail exigem configuração própria de Brevo/remetente/APP_URL;
somente configurar PostgreSQL não habilita o envio real de recuperação de senha.

2.5 - Criar contas para demonstrar o fluxo
- Cadastrar contas pelo login.html; elas começam como USUARIO.
- Para administrar o banco LOCAL NOVO, cadastrar uma conta própria e promover
  somente essa conta. Substituir o e-mail abaixo pelo que acabou de cadastrar:
  docker compose exec postgres psql -U postgres -d findy -c "UPDATE usuarios SET papel='ADMIN' WHERE LOWER(email)=LOWER('email-da-conta@exemplo.com');"
- Conferir que somente uma linha foi atualizada. Sair/entrar e abrir admin.html.
  A conta ADMIN do site é diferente do usuário postgres que administra o banco.
- Na conta profissional, preencher o perfil, selecionar habilidades e cadastrar
  pelo menos um serviço ativo na categoria desejada em Meus serviços.
- Aprovar esse perfil no painel administrativo. Perfil/conta também devem estar
  ativos. Sem isso, é normal a categoria não exibir o profissional.
- Em outra conta, com telefone preenchido, solicitar um serviço. Conferir Meus
  pedidos > Enviados no cliente e Meus pedidos > Recebidos no profissional.
- Aceitar/recusar na conta profissional e atualizar o pedido na conta cliente.
  Esse roteiro verifica o fluxo real, sem depender dos registros fictícios.

2.6 - Consultar as tabelas e provar a persistência
Sem instalar um gerenciador gráfico, abrir outro terminal na raiz:
  docker compose exec postgres psql -U postgres -d findy
Dentro do psql, executar:
  \dt
  SELECT id, nome, papel, ativo FROM usuarios ORDER BY id;
  SELECT id, usuario_id, status_aprovacao, ativo FROM prestadores ORDER BY id;
  SELECT id, titulo, categoria_id, preco, preco_maximo, ativo FROM servicos ORDER BY id;
  SELECT id, cliente_id, servico_id, status, data_solicitacao FROM solicitacoes ORDER BY id;
  \q
Os SELECTs consultam os registros salvos; não alteram dados. Não é necessário
mostrar senhas, hashes, tokens ou outros dados privados para demonstrar o banco.
Depois, atualizar as páginas ou reiniciar somente o backend e consultar o pedido
de novo: o registro e sua situação devem continuar salvos no PostgreSQL.

Se preferir um gerenciador PostgreSQL já instalado, configurar a conexão LOCAL:
host localhost; porta 5433; banco findy; usuário postgres; senha do próprio .env.
Ao terminar: Ctrl+C no backend e docker compose stop. Não apagar o volume.

3. ACESSAR O BACKEND DO SEU PC PELA MESMA REDE (OPCIONAL)
- Deixar Docker e backend rodando no seu computador.
- Descobrir seu endereço IPv4 da rede pelo ipconfig; o colega abre, por exemplo,
  http://IP-DO-SEU-PC:8080/index.html, substituindo IP-DO-SEU-PC pelo IPv4 correto.
- Precisa estar na mesma rede e a rede/firewall deve permitir essa conexão na
  porta 8080. Não desativar o firewall nem abrir a porta do banco na internet.
- Nesse cenário, os dois usam o banco do SEU computador por meio da API.
  O colega não precisa de Live Server ou banco local. Não precisa expor a porta
  5433: ela fica restrita ao próprio PC, como configurado no Compose.
- localhost sempre aponta para o computador de quem abre o navegador; enviar
  http://localhost:8080 para um amigo não aponta para o seu computador.
- Esse acesso termina se seu PC/backend parar ou se o endereço da rede mudar.
  Para pessoas em redes diferentes, o caminho previsto é a publicação no Render.

RESUMO SOBRE LIVE SERVER E DADOS
Live Server serve arquivos do frontend, mas não inicia o Java nem o PostgreSQL.
As APIs são necessárias para cadastro, login, catálogo e pedidos. O uso padrão
é abrir tudo na porta 8080. O suporte alternativo atual a Live Server é local,
na porta 5501; não serve como compartilhamento automático do seu backend/banco.
Git transmite código/SQL, não os registros de um banco que já está funcionando.
Cada instalação local começa com dados próprios; no site publicado os dados
são os do Neon. Copiar dados entre ambientes exige exportação/importação
combinada separadamente, sem compartilhar credenciais para isso.
